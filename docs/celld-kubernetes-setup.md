# celld Kubernetes Operations Runbook

This runbook is for platform administrators operating the celld Fleet in the
vcluster and the Ceph RGW in the home cluster.
Add celld Workers only from approved operations environments.
Do not store credentials used by `celld deploy` in Git or CI.

## Configure kubectl contexts

Operating the host cluster and vcluster through the current context risks
changing a same-named resource in the wrong cluster.
In the same shell session used for the steps below, enter and verify the
context name for each target.
Empty values and identical contexts are rejected.

```bash
read -r -p 'host Kubernetes context: ' HOST_CONTEXT
read -r -p 'celld vcluster Kubernetes context: ' VCLUSTER_CONTEXT
test -n "$HOST_CONTEXT"
test -n "$VCLUSTER_CONTEXT"
test "$HOST_CONTEXT" != "$VCLUSTER_CONTEXT"
readonly HOST_CONTEXT VCLUSTER_CONTEXT
kubectl --context "$HOST_CONTEXT" cluster-info
kubectl --context "$VCLUSTER_CONTEXT" cluster-info
```

If either displayed cluster is not the expected target, or you cannot clearly
identify both contexts, stop before performing any further operation.

## Verify storage and Fleet startup

After Flux applies the resources, wait first for `CephObjectStore/celld` and
then for `ObjectBucketClaim/celld-storage` to become Ready.

```bash
kubectl --context "$HOST_CONTEXT" -n rook-ceph wait \
  --for=jsonpath='{.status.phase}'=Ready \
  cephobjectstore/celld --timeout=10m
kubectl --context "$HOST_CONTEXT" -n app wait \
  --for=jsonpath='{.status.phase}'=Bound \
  objectbucketclaim/celld-storage --timeout=10m
```

Only the `celld-storage` Secret generated by the OBC is synchronized into the
vcluster's `celld` namespace.
The ConfigMap remains in the host cluster's `app` namespace.
The following commands list only the data key names for each resource. They do
not decrypt or print Secret values.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld get secret celld-storage \
  -o go-template='{{range $key, $_ := .data}}{{printf "%s\n" $key}}{{end}}' | sort
kubectl --context "$HOST_CONTEXT" -n app get configmap celld-storage \
  -o go-template='{{range $key, $_ := .data}}{{printf "%s\n" $key}}{{end}}' | sort
```

Next, wait for the three-Pod StatefulSet rollout and confirm that all three
Pods are Ready.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld rollout \
  status statefulset/celld --timeout=10m
kubectl --context "$VCLUSTER_CONTEXT" -n celld get pods -l app=celld
```

The RGW endpoint and peer port `8081` are cluster-internal only.
Do not add an externally reachable Service, Ingress, NodePort, or persistent
tunnel.
During deployment only, an approved operator may use a temporary port-forward
from the host context as described below.

## Diagnose Fleet-to-bucket connectivity

Diagnose bucket connectivity from inside the Fleet.
Credentials are passed through the Pod environment, so do not place their
values in the command line or output.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld exec celld-0 -- \
  celld diagnose \
  --bucket s3://celld \
  --endpoint http://rgw.celld.svc.cluster.local:80 \
  --region us-east-1
```

## Deploy a Worker

Only an approved operator who can handle the same `celld-storage` credentials
used by the runtime may perform this operation.
Unauthorized users must not run `celld deploy`.
Do not leave credentials in shell history, Git, CI, Kubernetes manifests, or
logs.

The operator environment must contain the Worker project source, the `celld`
CLI, `esbuild`, and connectivity to RGW.
Use an approved secret delivery mechanism to inject the same values as the
`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` keys in the synchronized
`Secret/celld-storage` into the operator process environment.
Do not enter the values manually or paste them into this runbook.
Set the Worker project root as the current directory and verify the required
environment variables and tools.

```bash
: "${AWS_ACCESS_KEY_ID:?supply the celld-storage access key securely}"
: "${AWS_SECRET_ACCESS_KEY:?supply the celld-storage secret key securely}"
command -v celld >/dev/null
command -v esbuild >/dev/null
```

Keep RGW private and forward only the host-context Rook RGW
`service/rook-ceph-rgw-celld` in the `rook-ceph` namespace to the operator's
loopback interface temporarily.
Start the port-forward in the background and verify connectivity, then deploy
the current-directory Worker project directly to the bucket using the same
bucket and region as the runtime and the forwarded endpoint.

```bash
RGW_PORT_FORWARD_LOG="$(mktemp)"
kubectl --context "$HOST_CONTEXT" -n rook-ceph port-forward \
  service/rook-ceph-rgw-celld 18080:80 >"$RGW_PORT_FORWARD_LOG" 2>&1 &
RGW_PORT_FORWARD_PID=$!
cleanup_rgw_port_forward() {
  trap - EXIT HUP INT TERM
  kill "$RGW_PORT_FORWARD_PID" 2>/dev/null || true
  rm -f "$RGW_PORT_FORWARD_LOG"
}
trap cleanup_rgw_port_forward EXIT HUP INT TERM
if ! timeout 30 sh -c \
  'until curl --silent --show-error --output /dev/null --max-time 1 http://127.0.0.1:18080/; do sleep 1; done' || \
  ! kill -0 "$RGW_PORT_FORWARD_PID" 2>/dev/null; then
  tail "$RGW_PORT_FORWARD_LOG" >&2
  exit 1
fi
celld deploy . \
  --bucket s3://celld \
  --endpoint http://127.0.0.1:18080 \
  --region us-east-1
```

After deployment finishes, exit the shell or run
`cleanup_rgw_port_forward` to close the temporary tunnel.

## Verify the client after deployment

Use the MagicDNS URL only for client verification after deployment, not as the
deployment endpoint.
The celld client endpoint is exposed only through the Tailscale Ingress.
Retrieve the Ingress address, open the displayed hostname from a device
connected to Tailscale, and verify that the Worker can reach the Fleet.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld get ingress celld
kubectl --context "$VCLUSTER_CONTEXT" -n celld get ingress celld \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}{"\n"}'
```

For example, if the address is `celld.example.ts.net`, use
`https://celld.example.ts.net/` as the client verification URL.

## Credential rotation and troubleshooting

After OBC credential rotation, use the commands above to verify the key names
in the vcluster-side `celld-storage` Secret and the host-side `ConfigMap` in the
`app` namespace.
Do not compare or print the values.
Environment variables are not updated automatically in existing Pods, so
restart only one Pod at a time and verify readiness, Fleet diagnostics, and
MagicDNS reachability after each restart.
Maintain availability by having the operator delete only one Pod at a time and
confirming readiness and diagnostics before deleting the next Pod.
The PodDisruptionBudget protects two Pods from voluntary disruptions through
the Eviction API, but it does not prevent a direct `kubectl delete pod`.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld delete pod celld-0
kubectl --context "$VCLUSTER_CONTEXT" -n celld wait \
  --for=condition=Ready pod/celld-0 --timeout=10m
kubectl --context "$VCLUSTER_CONTEXT" -n celld exec celld-0 -- \
  celld diagnose \
  --bucket s3://celld \
  --endpoint http://rgw.celld.svc.cluster.local:80 \
  --region us-east-1
```

Repeat the same operation for `celld-1` and `celld-2` only after the previous
Pod is Ready and diagnostics pass.
If a problem occurs, do not increase the number of stopped Pods; inspect the
state with the explicit vcluster context.

```bash
kubectl --context "$VCLUSTER_CONTEXT" -n celld describe pod celld-0
kubectl --context "$VCLUSTER_CONTEXT" -n celld logs celld-0
```

Do not retrieve, print, or paste Secrets into logs.
